# skill-show — design

Status: spec, agreed with the user on 2026-10-18. Not implemented yet.
Target: `dev/skill-show/` in this repository.
Workflow for the builder: superpowers `writing-plans`, then implementation with TDD.
Everything the builder needs is below; open questions are marked as such.

Marking used in this spec:

- **User decided**: the user chose this. Do not change it without asking.
- **Spec author decided**: chosen while writing the spec, with a reason. The builder
  may change it only for a concrete technical reason, and says so in the commit.
- **Observed**: seen on the author's machine on 2026-10-18 (Claude Code 2.1.302).
  It is not documented by Anthropic and may change with a Claude Code update.

## Intent and why

The user works with many skills and slash commands: her own, generated ones (from
her notes via `kios sync`), synced ones from claude.ai, and ones from plugins. They
live in at least seven places on disk. When she wants to know what a skill actually
tells the agent, she has to find the file first, and then she usually asks a model
to read it — which means a model reads, filters and summarizes text that she wanted
to see unfiltered.

`skill-show <name>` finds the file Claude Code would use for `/<name>` and prints it
**byte for byte**, with its path in front. No model is involved. The main use is
inside Claude Code with `! skill-show <name>`: the `!` prefix runs the command in a
shell and puts the output into the chat unchanged. It works the same way in a
normal terminal.

## Goals

1. `skill-show <name>` prints where the skill or command lives and then its content,
   unchanged, like `cat`.
2. Names work with or without a leading slash (`teamwork-tasks`, `/teamwork-tasks`)
   and in plugin form (`superpowers:brainstorming`, `/superpowers:brainstorming`).
3. For files generated by `kios sync`, the header also names the source note, as a
   full path when it can be resolved.
4. `skill-show` without an argument lists every name it finds, grouped by place. Not
   interactive by default; with a terminal and `fzf` it offers a picker.
5. A name that exists in several places shows which one Claude Code uses, and lists
   the others with their paths.
6. A name that is not a file (a bundled skill of Claude Code, such as `simplify`)
   gets a clear message, not silence and not a bare "not found".
7. Works without a TTY (inside `!`) and without colour; all output is plain text.
8. Tests run in a throwaway `HOME` and project folder and never depend on the real
   machine.

## Non-goals (phase 1)

- Editing, creating, enabling or disabling skills, commands or plugins.
- Showing subagent definitions (`agents/*.md`), hooks, output styles, MCP servers or
  `CLAUDE.md` files. (Possible later; same mechanism.)
- Extracting bundled skills from the Claude Code program file.
- A grouped `skills` view in `recall` (phase 2) and switchable overviews (phase 3).
- Searching inside skill contents (`grep` does that).
- macOS and Windows support. Paths for the managed (enterprise) folder on macOS are
  named for completeness only.

## Anti-goals (never)

- **Changing the content**: no trimming, wrapping, reflowing, re-encoding, stripping
  of front matter or HTML comments, no truncation of long files, no "smart"
  summaries. The bytes between the start and end lines are the bytes of the file.
- **Network access**: no `curl`, no `claude`, no API, no `git fetch`. Everything comes
  from local files.
- **Writing outside its own scope**: skill-show writes nothing at all in phase 1 —
  not into `~/.claude`, not into the project, not into the vault, no cache, no state
  file. (Phase 3 may read a config file; it still writes nothing.)
- **Calling a model** or any program that might (for example `claude -p`).
- **Guessing silently**: when it cannot tell which file Claude Code uses, it says so.

## Constraints

- **Bash**, like `wt` and `recall`: `#!/usr/bin/env bash`, `set -euo pipefail`, Bash
  5 (associative arrays are fine; `recall` uses them). Must pass `bash -n` and
  `shellcheck` with the same CI settings as the other tools.
- Required tools: Bash, coreutils, `awk`, `sed`, `find`, `jq` (for
  `installed_plugins.json`, `manifest.json`, `plugin.json`, `settings.json`).
  Optional: `fzf` (picker), `bat` (`--pretty`).
- `jq` missing: phase 1 still shows personal, project and enterprise skills and
  commands; plugin sources are skipped **with a visible note** on stderr naming the
  install command (`sudo dnf install jq`). A `plugin:skill` argument without `jq` is
  an error (exit 2). Spec author decided: one missing optional dependency should not
  hide the rest, but nothing is skipped silently (repo principle "no silent fallbacks").
- Folder layout as in the other tools:

  ```
  dev/skill-show/
    skill-show          the script (executable)
    README.md           usage, requirements, setup, where it looks, precedence
    test_skill_show.sh  tests
    example.conf        anonymized config example
  ```

  No `DESIGN.md` needed; this spec is the design. The builder may add one if the
  implementation diverges.
- Repo integration, part of phase 1:
  - row in the **Tools** table of the top-level `README.md`
  - `bash -n`, `shellcheck` and `bash dev/skill-show/test_skill_show.sh` in
    `.github/workflows/ci.yml`
  - add `dev/skill-show/skill-show|dev/skill-show/test_skill_show.sh` to
    `is_ci_shell` in `.githooks/pre-commit` (the comment there says to keep it in
    sync with `ci.yml`)
- Messages and help text in **English**. Spec author decided: the repo docs and the
  newest tool (`recall`) use English; `wt` is German for historical reasons.
- Config file `~/.config/skill-show/skill-show.conf`, sourced if present, every
  variable optional (same pattern as `recall`). Machine-specific values never go into
  the repository; `example.conf` is anonymized.
- Setup like the other tools: `ln -s "$PWD/dev/skill-show/skill-show" ~/.local/bin/skill-show`.

## Decided (by the user)

- Purpose: transparency; see the content 1:1 without a model reading it.
- Main path: `! skill-show <name>` inside Claude Code (no TTY there, so nothing
  interactive), and the same in a normal terminal.
- Name `skill-show`, part of this repo.
- Argument with or without leading slash, also `plugin:skill`.
- Default output: path first (for kios-generated commands also the vault source as a
  full path), then the file content unchanged.
- Pretty display only optional or on a TTY — the spec author decides (see below).
- No argument: list of all names with place/group, not interactive; with TTY and
  `fzf` optionally a picker.
- Ambiguous names: show all matches with paths; document the precedence rule.
- Bundled skills: clear message instead of silence.
- `recall` integration and switchable overviews are phases 2 and 3, not phase 1.
- Tests in `test_skill_show.sh` with an artificial `HOME` and project folder.

## Behaviour in detail

### Command line

```text
skill-show <name>            show the file Claude Code uses for /<name>, then list shadowed ones
skill-show <name> --all      show the content of every match, in precedence order
skill-show <name> --path     print only the path of the active match (one line), nothing else
skill-show <name> --raw      print only the content, no header or end line (for diff, pipes)
skill-show <name> --pretty   content through bat (colour only; text unchanged)
skill-show                   list (no TTY, or no fzf) / picker (TTY on stdin and stdout, fzf present)
skill-show --list            always the plain list, even on a TTY
skill-show --tsv             machine-readable list, one entry per line (stable; used by phase 2)
skill-show --help
```

`--path`, `--raw`, `--all` and `--pretty` can be combined where it makes sense;
`--path` with `--all` prints every matching path, one per line. Unknown options:
usage on stderr, exit 2.

**Spec author decided — default is plain `cat`, also on a TTY.** Reasons:
(1) the whole point is that what she sees is exactly what the agent gets;
(2) `glow` renders Markdown and in doing so hides HTML comments — including the
`kios:generated` marker — and reflows text, so it is not used at all;
(3) the output is the same in a terminal and in `!`, which keeps the tests simple
and the behaviour predictable. `--pretty` uses `bat --language=markdown
--style=plain --paging=never` (colour only, no line numbers, no pager, text
unchanged); without `bat` it prints a note on stderr and falls back to plain output.
The header and end line are never sent through `bat`.

### Name normalization

1. Strip one leading `/`.
2. Split at the first `:` into `<plugin>` and `<skill>`; no `:` means an unprefixed
   name.
3. Allowed characters per part: ASCII letters, digits, `. _ -`. Anything else (also
   `/`, `..`, spaces, an empty part, a second `:`) is refused with exit 2, so a name
   can never become a path outside the search folders. Use an ASCII-only check (like
   `re_ascii` in `wt`: under `de_DE`, `[A-Za-z0-9]` also matches umlauts).
4. Matching is case-sensitive. Spec author decided: Claude Code names are
   lower-case in practice, and a case-insensitive match could show a file that `/X`
   does not run. (Builder: if Claude Code turns out to match case-insensitively,
   follow it and note it in the README.)

### Where it looks

`$CLAUDE_HOME` below means `${CLAUDE_CONFIG_DIR:-$HOME/.claude}`. (Claude Code reads
`CLAUDE_CONFIG_DIR` to relocate `~/.claude`. Builder check 2026-10-18: documented on
code.claude.com/docs/en/env-vars, "All settings, session history, and plugins are
stored under this path".) The project root `$PROJECT` is
`git rev-parse --show-toplevel` from the current directory, else the current
directory; `--project <dir>` overrides it (also useful for tests).

| # | Group | Path pattern | Invoked as | Source |
|---|---|---|---|---|
| 1 | managed | `$MANAGED_DIR/.claude/skills/<dir>/SKILL.md`; `$MANAGED_DIR` = `/etc/claude-code` on Linux (`/Library/Application Support/ClaudeCode` on macOS) | `/<name>` | docs |
| 2 | personal skill | `$CLAUDE_HOME/skills/<dir>/SKILL.md` (a `<dir>` may be a symlink, e.g. `zeiterfassung -> ~/PycharmProjects/arbeitszeiten/claude-skill`) | `/<name>` | docs + observed |
| 3 | project skill | `$PROJECT/.claude/skills/<dir>/SKILL.md` | `/<name>` | docs |
| 4 | nested skill | `<dir>/.claude/skills/<d>/SKILL.md` for each directory from the current directory up to, but not including, `$PROJECT` | `/<name>` | docs |
| 5 | extra dir skill | `<dir>/.claude/skills/<d>/SKILL.md` for each `<dir>` in `EXTRA_DIRS` (config; stands in for `--add-dir`, which a separate process cannot see) | `/<name>` | docs |
| 6 | personal command | `$CLAUDE_HOME/commands/<name>.md` | `/<name>` | docs + observed |
| 7 | project command | `$PROJECT/.claude/commands/<name>.md` | `/<name>` | docs + observed |
| 8 | claude.ai skill | `$CLAUDE_HOME/skills/synced/<bucket>/<dir>/SKILL.md` | `/anthropic-skills:<name>` | observed |
| 9 | installed plugin | `<installPath>/skills/<dir>/SKILL.md` and `<installPath>/commands/<name>.md`, `installPath` from `$CLAUDE_HOME/plugins/installed_plugins.json` | `/<plugin>:<name>` | docs + observed |
| 10 | claude.ai plugin | `$CLAUDE_HOME/plugins/synced/<bucket>/<plugin>~g<N>/{skills/<dir>/SKILL.md,commands/<name>.md}` | `/<plugin>:<name>` | observed |

`MANAGED_DIR` can be overridden by the environment variable `SKILL_SHOW_MANAGED_DIR`
(tests need it; `/etc` is outside the fake `HOME`).

Rules per source:

- **Skill name**: front matter `name:` of `SKILL.md`; without one, the directory name.
  The docs say the directory name "also invokes the skill", so a skill whose `name:`
  differs from its folder is found under **both** names; the list shows the
  `name:` value and the folder in brackets. (Builder check 2026-10-18: the skills
  docs say "`name` sets the command that the `/` menu shows and that you type, unless
  another command already uses that name. The directory name also invokes the
  skill." No live test was run — the user decided to go without one — so both names
  are kept.)
- **Command name**: file name without `.md`. Commands in subfolders
  (`commands/<sub>/<name>.md`) are invoked as `/<sub>:<name>` — **changed by the
  builder** on 2026-10-18 from "listed under `<name>` with `<sub>` as a label": the
  skills docs call subfolders "the older format and still works" and name them as
  "Subdirectory path relative to `commands/` with each `/` replaced by `:`, then the
  file name without extension" (example `/frontend:component`). Consequences: a
  prefixed name is looked up in command subfolders (groups 6–7) as well as in groups
  8–10; a bare name does not match a subfolder command but the not-found message
  suggests it; if a subfolder and a plugin share the prefix, both are shown and the
  header says it cannot tell which one Claude Code uses. Without `jq`, a prefixed name
  that matches a subfolder command is shown with a note that plugins were not
  checked; otherwise it is the usual exit 2.
- **Skipped**: every entry whose name starts with `.` (observed:
  `~/.claude/skills/.trash/` holds deleted skills; `synced/` also has `.bucket-*`
  files), and the folder `synced` inside `$CLAUDE_HOME/skills` for groups 2–5 (it
  is group 8).
- **Plugin prefix** is `name` from `<pluginroot>/.claude-plugin/plugin.json`, not the
  folder name. Observed: the folder `pydantic-ai` has `"name": "ai"`, and its skill is
  invoked as `/ai:building-pydantic-ai-agents`. Fallback when `plugin.json` has no
  name: the key in `installed_plugins.json` before the `@` (`superpowers@claude-plugins-official`
  → `superpowers`).
- **Installed plugins: only the installed version counts.** Use `installPath` from
  `installed_plugins.json` (format observed: `{"version": 2, "plugins": {"<plugin>@<marketplace>": [{"scope": "user", "installPath": "...", "version": "..."}]}}`).
  Never glob the cache: observed are up to 14 old versions per plugin under
  `plugins/cache/claude-plugins-official/<plugin>/` and a temporary clone
  `plugins/cache/temp_subdir_*.clone/`. A `scope` other than `user` (project or
  local) counts only when its project path equals `$PROJECT`; the field name was not
  observed (all entries here are `user`). Builder check 2026-10-18: the plugin
  loading docs say only that the file "records each install with its `scope`,
  `installPath`, and `version`"; no project path field is documented. So such entries
  are included with the label `(scope: <scope>, project unknown)`.
- **Enabled or not**: a plugin whose key is `false` in `enabledPlugins` of
  `$CLAUDE_HOME/settings.json`, `$PROJECT/.claude/settings.json` or
  `$PROJECT/.claude/settings.local.json` is still listed and shown, labelled
  `(disabled)`. Spec author decided: transparency includes things that are switched
  off; hiding them would make "why is this not running?" harder. Order (builder check
  2026-10-18, settings and plugin loading docs): the sources "merge key by key. For
  each plugin id, the value that applies is the one from the highest-precedence source
  that mentions the id" — local > project > user.
- **claude.ai plugins (observed)**: `plugins/synced/<bucket>/manifest.json` lists
  `{"plugins": [{"name": "engineering", "generation": 3, ...}]}`, and the folder in
  use is `<name>~g<generation>` (it also contains an empty file `.in_use`). Older
  generations sit next to it (`engineering/`, without suffix). Use the manifest's
  generation; if the manifest is missing or unreadable, use the folder that contains
  `.in_use`; if neither works, skip that plugin with a note on stderr. The prefix
  again comes from `.claude-plugin/plugin.json`.
- **claude.ai skills (observed)**: `skills/synced/<bucket>/manifest.json` lists the
  skills (`{"skills": [{"name": "pdf", ...}]}`); this session shows them as
  `anthropic-skills:pdf`. Use the folders that the manifest names; without a
  manifest, every non-dot folder with a `SKILL.md`. The prefix `anthropic-skills`
  is a constant in the script (with a comment that it is observed, not documented);
  config `SYNCED_SKILL_PREFIX` overrides it.
- Missing folders or files are normal (most people have no managed folder, many
  repos no `.claude/`) and produce no message.

### kios-generated files

`kios sync` writes a marker comment into each file it generates:

```
<!-- kios:generated | Quelle: <relative path> | Nicht von Hand aendern - aendere die Quelle und fuehre `kios sync` aus. -->
```

Observed: the marker is **not always on line 4**. It is on line 4 or 5 in
`~/.claude/commands/*.md` (after front matter with one or two keys), and on line 1,
before the front matter, in the older files in
`~/GitRepos/Mathe_im_Advent/.claude/commands/`. kios itself recognizes a generated
file by `kios:generated` anywhere in the first 2000 characters
(`is_generated()` in the kios source). skill-show uses the same rule: search the
first 2000 bytes for `kios:generated | Quelle: ` and take the text up to the next ` |`.

Resolving the source:

- The value is relative. Observed values: `40-runbooks/<file>.md` (relative to the
  vault) and `templates/<file>.md` (relative to kios' own template folder, and not a
  literal path: `templates/kios-merken.md` lives at
  `<kios repo>/templates/agent/system-commands/kios-merken.md`; the older
  `templates/merken.md` no longer exists anywhere).
- Config `SOURCE_ROOTS=(…)`: folders tried in order; the first `<root>/<value>` that
  exists is printed as a full path (`realpath`). The example config shows the vault
  and the kios template folder.
- Not resolvable (no config, or no root has the file): print the raw value and say
  so — `source: templates/merken.md (kios; not found under SOURCE_ROOTS)`. Never
  guess a path.
- skill-show only checks that the source file exists; it does **not** read or print
  it. (The vault may contain sensitive notes; the user decides whether to open it.)
- Spec author decided: the marker detection is kios-specific in phase 1. It is one
  small function; a generic "generated by" pattern list can come later if a second
  generator appears.

### Precedence and ambiguous names

For an unprefixed name, matches are ordered:

1. managed skill
2. personal skill
3. project skill
4. nested skill(s) (nearest to the current directory first)
5. extra dir skill(s)
6. personal command
7. project command

The first match is labelled `active`; the others `shadowed by <group>`, except
nested skills next to a project skill: the docs say "both load", so they are
labelled `also loaded`.

Documented (code.claude.com/docs/en/skills, read 2026-10-18): enterprise > personal
> project; a skill beats a command file of the same name; plugin skills never
collide because of their prefix; project root and nested skill both load.
**Not documented: a command at a higher level against a skill at a lower level**
(e.g. personal command vs. project skill). Spec author decided: all skills before all
commands, because "the skill wins" is the only documented rule between the two
kinds. The README states this order and marks that one case as unverified; the
header then says `active (by the precedence in the README)`. Builder 2026-10-18: no
live test was run (creating dummy skills and commands was blocked by the permission
check, and the user decided to go without one), so the order and the marking stay.
The skills docs row "A skill and a file in `.claude/commands/` | The skill" does not
say whether a personal `~/.claude/commands/` file counts.

A prefixed name (`plugin:skill`) looks only in groups 8–10, plus command subfolders
(see "Command name"). Two installed plugins
with the same `plugin.json` name (different marketplaces) are listed together; both
are shown as matches, the header says it cannot tell which one Claude Code uses, exit
code 0 if it printed content (`--all` implied), and the README documents it.

**Spec author decided — bare names do not fall through to plugins.** `skill-show
code-review` must not show `engineering:code-review`: `/code-review` runs Claude
Code's bundled skill, not the plugin skill. When a bare name has no file match, the
not-found message lists prefixed matches as suggestions ("Did you mean
`/engineering:code-review` (plugin skill)?").

### Output format

Header and end line go to **stdout** together with the content. Spec author decided:
for this tool the path is part of the result (the user asked for "path first"), and
`--raw`/`--path` and pipes stay clean. (Observed 2026-10-18, Claude Code 2.1.302:
`!` puts stderr into the chat too, merged into the stdout block — see Open question
3.) Notes about
skipped sources and suggestions go to stderr, as in `wt` and `recall`. `--raw` and
`--path` print no header.

Example (paths from the author's machine; content abbreviated here only):

```text
$ skill-show /teamwork-tasks
==> /teamwork-tasks · command · personal · active
    file:    /home/katha/.claude/commands/teamwork-tasks.md
    source:  /home/katha/ki-os/40-runbooks/teamwork-tasks-anlegen.md (kios sync: edit the source, not this file)
    > cat '/home/katha/.claude/commands/teamwork-tasks.md'
──── begin ────
---
description: Offene Themen, die sich in Claude-Sessions in `.reviews/offene-themen.md` sammeln, gesammelt als Tasks in...
---
<!-- kios:generated | Quelle: 40-runbooks/teamwork-tasks-anlegen.md | Nicht von Hand aendern - aendere die Quelle und fuehre `kios sync` aus. -->
…the rest of the file, unchanged…
──── end of /home/katha/.claude/commands/teamwork-tasks.md ────
```

```text
$ skill-show zeiterfassung
==> /zeiterfassung · skill · personal · active
    file:    /home/katha/.claude/skills/zeiterfassung/SKILL.md
    link:    /home/katha/PycharmProjects/arbeitszeiten/claude-skill/SKILL.md
    more:    <other files in the skill folder, one full path per line, or "none">
    > cat '/home/katha/.claude/skills/zeiterfassung/SKILL.md'
──── begin ────
…
──── end of /home/katha/.claude/skills/zeiterfassung/SKILL.md ────
```

```text
$ skill-show superpowers:brainstorming
==> /superpowers:brainstorming · skill · plugin superpowers 7.0.0 (claude-plugins-official)
    file:    /home/katha/.claude/plugins/cache/claude-plugins-official/superpowers/7.0.0/skills/brainstorming/SKILL.md
    …
```

Rules:

- The `> cat '<path>'` line is the repo's explain-then-run principle: it names the
  equivalent command, so the user can reproduce the output herself. The content is
  read exactly that way (`cat -- "$file"`), not through `read` loops or `echo`,
  which would alter backslashes, NUL bytes or a missing final newline.
- `link:` appears only when the path contains a symlink; it shows the `realpath`.
- `more:` lists the other files of a skill folder (e.g. `pdf/REFERENCE.md`,
  `pdf/FORMS.md`, `scripts/…`), recursively, sorted, as full paths, without showing
  their content. Skills only; capped at 50 lines with `… n more` (it is metadata,
  not content, so the cap does not touch the no-truncation rule).
- If the file does not end with a newline, the end line is preceded by one newline
  and the end line says `(no newline at end of file)`, so the content stays
  byte-identical and the marker still starts on its own line.
- Shadowed matches follow after the end line, one per line:
  `    shadowed: /<name> · skill · project · <path>` (with `--all` their full blocks
  follow instead).
- The begin and end lines must be distinctive enough that a model reading the chat
  can tell where the file starts and stops; exact characters are left to the builder.
- No colour in the header unless stdout is a TTY and `NO_COLOR` is unset; content is
  never coloured except with `--pretty`.

### List without argument

Plain text, one group heading per source, entries sorted by name, the invocation
form (with `/`) on each line. Example (abbreviated):

```text
personal skills  /home/katha/.claude/skills
  /zeiterfassung                         -> /home/katha/PycharmProjects/arbeitszeiten/claude-skill
personal commands  /home/katha/.claude/commands
  /arbeit-verteilen                      kios: 40-runbooks/arbeit-auf-subagenten-verteilen.md
  /kios-merken                           kios: templates/kios-merken.md
project commands  /home/katha/GitRepos/Mathe_im_Advent/.claude/commands
  /merken                                kios: templates/merken.md
claude.ai skills  /home/katha/.claude/skills/synced/<bucket>
  /anthropic-skills:pdf
plugin superpowers 7.0.0  /home/katha/.claude/plugins/cache/claude-plugins-official/superpowers/7.0.0
  /superpowers:brainstorming
claude.ai plugin engineering (generation 3)  …/plugins/synced/<bucket>/engineering~g3
  /engineering:code-review
not files: bundled skills and built-in commands of Claude Code (see skill-show --help)
```

- A shadowed entry gets `(shadowed by <group>)` at the end of its line.
- A disabled plugin gets `(disabled)` in its group heading.
- The list shows the kios source as the raw relative value (it is a list, not a
  lookup; resolving every entry would cost a stat per root).
- `--tsv`: one line per entry, tab-separated, no header, stable column order for
  phase 2:
  `<invocation>\t<kind skill|command>\t<group>\t<name>\t<file>\t<status active|shadowed|also-loaded|disabled>\t<kios source or empty>\t<description from front matter or empty>`.
  Values with a tab or newline are cleaned (tab/newline → space) in this output
  only; the README says so.

**Picker** (stdin and stdout are a TTY, `fzf` is in `PATH`, no `--list`): the list
entries without group headings go to `fzf` with the group as a dimmed field and a
preview of `skill-show --raw <name>`; `enter` prints the normal output for that name
to stdout and exits; `esc` exits 130 without output. Inside `!` there is no TTY, so
the plain list is printed — the picker can never hang a Claude Code session.
Builder: keep the fzf options to those already used by `recall` (fzf 0.74 is
installed); the picker is small and not the main use.

### Not found and bundled skills

Observed: Claude Code 2.1.302 is a single program file
(`~/.local/share/claude/versions/2.1.302`, ELF, about 285 MB; `claude` in `PATH` links
to it). Bundled skills such as `simplify`, `code-review`, `fewer-permission-prompts`,
`loop` have no `SKILL.md` anywhere on disk: a search of the whole file system for
folders of those names found nothing, and the description text of
`fewer-permission-prompts` occurs as a string inside the program file. So their text
cannot be shown 1:1 from a file.

For a name with no file match, print to stderr and exit 1:

```text
skill-show: no file for /simplify.
  It is not in any place skill-show looks (skill-show --help lists them).
  If /simplify appears in Claude Code's / menu, it is most likely a bundled skill or a
  built-in command: its text is compiled into the Claude Code program and there is no
  file to show.
  (only when prefixed matches exist, e.g. for `skill-show code-review`:)
  Plugin skills with this name: /engineering:code-review
```

- Config `BUILTIN_NAMES=(…)` (default empty; `example.conf` lists the ones the
  author's session shows): when the name is in it, the message says "is a bundled
  skill or built-in command of Claude Code" instead of "most likely". Spec author
  decided: a list hard-coded in the script would go stale with every Claude Code
  update; a config list is the user's own claim.
- skill-show never tries to extract text from the program file (anti-goal: it is
  version-dependent, unofficial, and could show text that is not what runs).

### Exit codes

| Code | Meaning |
|---|---|
| 0 | content (or path, or list) printed |
| 1 | name not found (message on stderr) |
| 2 | usage error: unknown option, invalid name, `plugin:skill` without `jq` |
| 130 | picker cancelled with `esc` (as fzf) |

A file that exists but cannot be read is an error (`die`, exit 1, message names the
path), never an empty block.

## Phase 2 — `recall` gets a group "skills"

Not part of phase 1.

- `recall` shows a ☰-like group (own icon, e.g. `◇ skills`) with one entry per
  skill/command, built from `skill-show --tsv` (the shared search logic; `recall`
  calls it, it does not copy the code). Spec author decided: calling the other
  script keeps one implementation of the precedence rules; the cost is one process
  per list build.
- **Title problem**: `recall` takes a procedure's title from `title:` in the front
  matter, else the file name (`title_and_command` and `collect_procedures` in
  `dev/recall/recall`). For `SKILL.md` every entry would be called "SKILL". The skill
  group therefore uses column 1 of `--tsv` (the invocation, `/name` or
  `/plugin:name`, which comes from `name:` or the folder) as the title, and the
  description (column 8) as the dimmed explanation that typing can find.
- `enter` shows the entry through `skill-show <name>` (unrendered, by the 1:1 rule),
  not through `glow`; `ctrl-o` opens the file; `ctrl-y` copies the invocation.
- `recall`'s exact search finds skills by name and description.
- Tests in `test_recall.sh` with a stub `skill-show` that prints fixed `--tsv` lines.
- Open for that phase: whether shadowed and disabled entries appear in recall
  (suggestion: yes, dimmed).

## Phase 3 — switchable overviews

Not part of phase 1.

- Config in `~/.config/skill-show/skill-show.conf`, like `wt`/`recall`:
  `GROUPS=(personal project nested managed extra claude-ai-skills plugins claude-ai-plugins)`
  — the groups the list and picker show, in that order; a group left out is not
  listed (lookup by name still searches all places, so `skill-show <name>` never
  lies about what runs).
- Named overviews, e.g. `OVERVIEW_mine=(personal project)` and
  `OVERVIEW_plugins=(plugins claude-ai-plugins)`, chosen with
  `skill-show --list mine`; `recall` (phase 2) can use the same names.
- Per-plugin hide list `HIDE_PLUGINS=(…)` for plugins that are installed but never
  used.
- Still read-only; no state files.

## Open questions

1. **Bundled skill text**: is there an official way in the current Claude Code to
   print the text of a bundled skill (a CLI subcommand or a documented file)? The
   author knows none. If one exists, phase 1 may call it for not-found names — but
   only if it is local (no network) and prints the text unchanged; otherwise keep the
   message.
   **Resolved 2026-10-18 (builder):** none found. The skills docs only say "Bundled
   skills are prompt-based"; no CLI command prints their text. The message stays.
2. **Precedence across kinds and levels** (personal command vs. project skill of the
   same name) is not documented. See "Precedence"; decide by a live test if possible.
   **Still open 2026-10-18:** no live test (blocked by the permission check; the user
   decided to go without). The spec order stays, the header and README mark the case
   as unverified.
3. **Does Claude Code's `!` output include stderr?** It decides whether the notes on
   stderr are visible in the chat. The design does not depend on it (everything the
   user asked for is on stdout); the README should state the observed behaviour.
   **Resolved 2026-10-18 (observed by the user, Claude Code 2.1.302):**
   `! sh -c 'echo OUT; echo ERR >&2'` shows both `OUT` and `ERR` in the chat, merged
   into the stdout block (the stderr block stays empty). So the notes on stderr are
   visible in the chat. Not documented; may change with an update.
4. **claude.ai synced folders** (`skills/synced`, `plugins/synced`, the `~g<N>`
   generations, the `anthropic-skills` prefix) are observed, not documented. If a
   Claude Code update changes them, the related tests still pass (they use the
   fixture) but the real lookup breaks — the README should say these two groups are
   best-effort.
5. **Case sensitivity** (builder, 2026-10-18): the skills docs mention ignoring case
   only when synced claude.ai skills collide with local ones; general name matching is
   not documented and not live-tested. Matching stays case-sensitive as decided above.
